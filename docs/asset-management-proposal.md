## 1. 背景・目的

lsir-cs（LIST Sotheby's International Realty 向け業務管理ツール）は、これまでタスク管理・バイヤーリスト・CRM（顧客管理）・プロジェクト管理を中心に発展してきた。

今回、**Wealth Park** や **GMOの賃貸DX** のような不動産管理会社向け「オーナーポータル・資産管理」サービスを参考に、物件・オーナー・賃貸契約・賃料入出金を一元管理できる独自の資産管理CRM機能を追加する。

**参考にする観点**（機能コンセプトのみ。デザイン・商標・実装コードは一切模倣しない）:
- オーナーごとの物件ポートフォリオ管理
- 賃貸契約の一元管理
- 月次の賃料入金状況・オーナーへの送金予定額の可視化

> 機能コンセプトやビジネスモデル自体は著作権・特許で保護される対象ではないため、参考にした独自実装を行うこと自体に法的な問題はない（ロゴ・ブランド名・具体的なUIデザインの模倣は行わない）。

- 国内の同種SaaS（いえらぶCLOUD等）では「入金予定額 vs 実績額」から物件別・オーナー別の月次収支報告書を作る一般的パターンが確認できた。現行の`AssetRentTransactions`（`expectedAmount`/`receivedAmount`、`yearMonth`単位）はこのパターンと構造的に合致しており、フェーズ2の収支ダッシュボードの土台として妥当
- 両社とも技術スタックの公開情報はほぼ無く（クローズドな商用SaaS）、模倣すべき/参照できる具体的な実装情報は無い。今回の設計判断はあくまで自社の技術スタック（Azure SWA + Functions + Cosmos DB）に即した独自方式で妥当

## 2. 課題・解決したいこと

- 物件・オーナー・契約・賃料入出金の情報が分散しており、一元管理する手段がない
- 既存のタスク管理システムに直接機能を足すと、並行して進んでいるタスク管理自体のアップデート作業と競合し、使い勝手を損なうリスクがある

## 3. 対象ユーザー

- フェーズ1: 社内の管理者ユーザーのみ（テスト運用）
- 将来的には、担当者・オーナー自身がアクセスできるポータル機能への拡張も視野に入れる（フェーズ2以降で検討）

## 4. 開発方針

1. 既存のタスク管理システムとは完全に隔離して開発する
   - 別ブランチ（`claude/crm-asset-management-system-0bs8i0`）で開発・検証
   - ナビゲーションには管理者限定の新アイコンとして追加し、一般ユーザーの画面には一切影響させない
2. 実用段階に達するまで `main` へはマージしない
3. **実際の送金・決済は一切行わない**。フェーズ1では入出金の「記録・集計」のみを扱う方針を堅持する

### 5.1 フェーズ2: 物件別収支ダッシュボード（実装済み）

**課題**: 現状の `AssetRentTransactions` は収入（入金予定額・入金実績額）とオーナーへの送金予定額のみを記録しており、修繕費・管理委託手数料の実費・保険料・固定資産税といった**支出**を記録する場所がない。そのため「この物件は今月いくら儲かっているか／赤字か」が見えない。

**実装内容**:
1. 新規エンティティ `AssetExpenses`（支出記録）を追加: `propertyId`・`category`（修繕費/管理委託手数料/保険料/固定資産税/その他）・`yearMonth`・`amount`・`paidDate`・`vendor`・`notes`
2. 新規タブ「収支ダッシュボード」を追加: 物件を選択すると、月次の 収入（`AssetRentTransactions.receivedAmount`の合計）／支出（`AssetExpenses.amount`の合計）／収支（収入-支出）を直近12ヶ月分の推移グラフ＋一覧表で表示
3. オーナー様の要望を受け、Wealth Park画面を参考にした**グリッド式収支入力**（`@mui/x-data-grid`、行＝収支項目・列＝月＋年間合計）を追加。賃料収入行・支出科目の行はセル編集可能（詳細は仕様書参照）
4. 集計はまずクライアント側で計算する簡易実装から始め、データ量が増えた場合に専用集計APIを検討する

### 5.2 フェーズ3: 社内チャットの土台（実装済み）

**オーナー様への回答（結論）**: はい、テスト環境レベルであれば**社内スタッフ間チャットは追加費用なしで今から実装可能**でした。ただし**オーナー・顧客向けチャットは別の理由でもう少し後（フェーズ4）が適切**と判断し、社内チャットのみを実装。

- **社内スタッフ間チャット**: 既存のホワイトリスト認証（社内ユーザーのみアクセス可）の仕組みがそのまま使えるため、新しいアクセス制御を作らずに済んだ。データ保存はCosmos DBの新規コレクション（`AssetChatThreads`・`AssetChatMessages`）を使い、表示更新は5秒おきのポーリング（`GetAssetChatMessages`を定期的に呼ぶだけ）で実現。Azure SignalR Serviceのような追加インフラ・追加費用なしで動作する
- **オーナー・顧客向けチャット**: 技術的には同じ仕組みで作れるが、現状のアクセス制御は「ホワイトリストに載っている社内ユーザーは全機能フルアクセス」という一枚岩のモデル。オーナー・顧客をログインさせる場合は「自分の物件・自分とのチャットだけ見える」という**限定アクセス権限モデル**を新設する必要があり、これは資産管理機能全体のセキュリティに関わる設計変更になる。そのため、フェーズ4の「オーナー・顧客向けポータル」と合わせて設計する
- **将来の本格リアルタイム化**: ポーリング方式は数秒の遅延はあるがテスト運用や社内利用では十分実用的。利用者数が増えて即時性が求められる段階になったら、Azure SignalR Service（無料枠あり）等への切り替えを検討する（フェーズ5）

**データモデル（実装済み）**: 詳細は `asset-management-spec.md` 2.6/2.7節を参照。

### 5.3 契約書類フォルダのリンク保存（フェーズ4の一部を前倒し・実装済み）

**オーナー様からの質問**: 「顧客にBoxのフォルダをリンクし、契約書類等を格納していけるか」

**回答（結論）**: 技術的には可能で、2段階の実装レベルを提示し、**レベル1（リンク保存のみ）を採用**した。

- **レベル1（採用）**: フォルダ作成・顧客への共有（コラボレーター招待や共有リンク発行）はBox側で従来通り手動対応し、そのリンクを `AssetContracts.documentsFolderUrl` として保存・表示するだけ。既存の`SpreadsheetView`のBox埋め込みと同じパターンの流用で、追加費用・新規のBox API設定なしで即日実装できた
- **レベル2（見送り・将来検討）**: 契約作成時に自動でBoxフォルダを作成し顧客を自動招待する完全自動化。Box Developer ConsoleでのカスタムAPPアプリ登録（Client ID/Secret）とAzureへの新規シークレット設定が必要で、オーナー様側の作業が発生するため今回は見送った
- **調査メモ**: このセッションに接続されているBoxアカウント（法人ドメイン、10GB割当）ではフォルダ作成・ファイルアップロード等のAPI操作は可能だったが、共有リンクの発行や外部コラボレーターの招待を行うツールは接続されているBox連携には含まれておらず、いずれにせよBox側UIでの手動対応が必要だった

## 6. リスク・制約

- **法務**: 商標・著作権の観点から、参考サービスのロゴ・ブランド名・UIデザインの直接模倣は行わない（機能コンセプトの参考のみ）
- **コスト**: Cosmos DBへの新規コレクション追加、Azure Static Web Appsのプレビュー環境の枠に留意する（詳細は運用メモ参照）
- **セキュリティ**: 送金・決済機能を持たない設計とすることで、金銭事故のリスクを構造的に排除する

- Azure Static Web Apps のプレビュー環境には上限があり、不要な古い環境は都度削除する運用とする
